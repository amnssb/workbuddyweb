# 发布流程与文档规范

## issue 回复的写法

**判据**：一个搜到这条 issue、但不读代码的用户，能否在 30 秒内知道「这问题修了没有」以及「我要不要做什么」。

公开 issue 的回复面向普通用户，不是排障笔记。检查器在 `dev/check_issue_reply.py`，提交前可运行：

```bash
python dev/check_issue_reply.py < draft-reply.md
```

### 内容红线

- **内部标识符**：不要出现反引号里的变量名、函数名、文件路径、提交哈希，例如 `_scope_models`、`keysvc.model_allowed`、`server/main.py`、`f20e6f9`。用户不知道这些是什么。
- **排障过程与自我检讨**：不要写「我的回复惯性」「排障笔记」「自我检讨」「顺手把……」这类维护者内心独白。
- **测试与验收清单**：不要罗列「验证：全量 1222 条通过」「e2e 全过」「浏览器验收 14 项全过」。用户不关心测试清单，只关心对他的影响。

### 口吻

像维护者本人在说话，别像客服。避免：

- 「感谢您的反馈！已修复。」
- 「希望这能帮助到您。」
- 「如有任何疑问，请随时与我们联系。」
- 「需要注意的是，该行为已改变。」

### **长度**

控制在 15 行以内，不要用多个小标题。一段话讲清：修了什么、用户是否需要操作、何时生效。

### 例外

用户原文里出现过的报错、路径、字段名可以引用，因为用户正是拿着这些内容搜进来的。
